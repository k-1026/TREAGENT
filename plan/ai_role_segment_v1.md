## 0. 한 줄 요약

- **세그먼트:** 나이대를 3개(20~30대 / 40~50대 가족 / 60대 이상)로 줄이고, 첫 발표는 **핵심 고객 1명**만 말한다. 추천은 20~30대(혼자·친구).
- **AI 역할:** 장소는 **코드가 고르고**, AI는 고른 장소의 **문장과 이유만** 쓴다. 이 원칙은 이미 기술 명세에 있다 (plan/spec/treagent_tech_spec_v1.md 15-1).
- **빈 곳:** 지금 코드는 연령대·테마를 입력으로 받지 않고, 코스도 1개(경로 2개)뿐이다. 발표에서는 "설계"와 "지금 구현"을 나눠서 말해야 한다.

## 2. 고객 세그먼트

### 2-1. 왜 3개로 줄이나

- 나이대를 5개로 나누면 세그먼트마다 코스가 필요한데, 지금 코스는 1개(경로 2개)뿐입니다 (1번).
- 장소 표에 연령 적합도 열이 없어서, 나이대를 잘게 나눠도 점수를 다르게 줄 근거가 없습니다 (3번).
- 그래서 **이동 조건이 확실히 다른 3묶음**으로만 나눕니다. 나이 자체보다 "얼마나 걷나, 실내가 필요한가, 쉼터가 필요한가"가 다릅니다.

### 2-2. 세그먼트 표 (추천안)

| 세그먼트 | 핵심 테마 | 코스 특징 | 지금 데이터로 되나 |
|---|---|---|---|
| 20~30대 (혼자·친구) | 활동·데이트·친구 | 도보 중심, 골목·상권, 사진 미션 | 대체로 됨. C01 explore 경로가 이 성격 (1번) |
| 40~50대 (아이 동반 가족 포함) | 체험·가족 | 실내 체험 중심, 이동 짧게, 화장실·쉼터 확인 | 부족. 화장실 열 없음, 체험 프로그램 여부 `[확인 필요]` |
| 60대 이상 | 역사·쉬운 코스 | 이동 거리 짧게, 실내 역사관 중심, 쉼터 연결 | 부족. 계단 열 없음. 쉼터는 역할(shelter)로 일부 가능 (3번) |

### 2-3. 핵심 고객 1명: 두 후보 비교

| 기준 | 20~30대 (혼자·친구) | 40~50대 가족 |
|---|---|---|
| 기존 문서와 맞나 | 맞음. 1차 이용자 가설이 20–30대 혼행객 (10번) | 새로 세워야 함 |
| 지금 코스·데이터로 시연 | 가능 (C01 explore) | 화장실·체험 데이터가 없어 시연 근거 약함 |
| 폭염 대응 이야기 | 실내 경로(indoor)로 설명 가능 | 더 설득력 있음(아이 동반은 더위 부담이 큼). 단 근거 수치는 아직 없음 `[미검증]` |
| 앱 사용 | 혼자 앱 보며 걷는 흐름과 맞음 | 보호자 1명이 앱을 들고 가족을 이끄는 흐름. 화면 설계 다시 봐야 함 |

- **판단:** 첫 발표의 핵심 고객은 **20~30대(혼자·친구)**를 추천합니다. 이유는 기존 가설과 이어지고, 지금 있는 코스·데이터로 바로 보여 줄 수 있어서입니다.
- 40~50대 가족은 "폭염 때 더 필요한 사람들"이라는 이야기가 강해서 **첫 번째 확장 세그먼트**로 말합니다.
- 설명할 때 "60대라서 골랐다"처럼 나이를 이유로 쓰지 않고, "평지이고 쉼터가 가까워서"처럼 이동 조건으로 말합니다.

### 2-4. 보완이 필요한 데이터

- 장소 표에 **테마 태그**(활동·체험·역사)와 **세그먼트 적합도** 열 추가.
- 40~50대·60대 이상을 위해 **화장실 여부, 계단·경사, 쉼터까지 거리** 열 추가. 값이 없으면 `확인 필요`로 둡니다.
- 코스는 세그먼트당 데모 1개씩, **총 3개**를 목표로 합니다 (지금 1개).

## 3. AI 작동 방식 (흐름도에 넣을 내용)

### 3-1. 6단계와 지금 구현 상태

| 단계 | 누가 | 하는 일 | 지금 상태 |
|---|---|---|---|
| 1. 입력 | 앱 | 날씨(예: 폭염), 시간대, 연령대, 테마 | 날씨·시간·위치는 받음. **연령대·테마는 아직 없음** (7번) |
| 2. 규칙 판정 | 코드 | 폭염이면 야외 제외, 실내 모드로 결정 | 구현됨. 28℃/33℃ 기준, 특보면 SAFETY (5번) |
| 3. 장소 필터 | 코드 | 검수된 장소 DB에서 모드·연령대에 맞는 장소만 남김 | 모드·운영시간 필터는 구현됨. **연령대 필터는 없음** (6번) |
| 4. 장소 선택 | 코드 | 남은 장소 중 3곳을 정해진 기준으로 고름 | 지금은 **코스별로 미리 정한 경로**를 고름(점수 선택 아님). 점수 기준은 설명 페이지 3절 안 (1번) |
| 5. 문장 생성 | AI | 고른 3곳의 제목·설명·이유 문장 | **P0는 승인 대사 빈칸 채우기, LLM 없음.** LLM 윤문은 P1 (9번) |
| 6. 검수 | 코드 | 허용 키워드·길이 규칙 통과 확인, 실패하면 승인 대사 | 원칙만 있음, 구현 전 (8번) |

### 3-2. 왜 이렇게 나누나 (판단)

- **안전 판단은 바뀌면 안 된다.** 폭염·운영시간·휴관 같은 판단을 AI에 맡기면 같은 조건에서도 답이 달라질 수 있습니다. 코드에 두면 같은 입력에 늘 같은 결과가 나오고, 운영자가 기준을 직접 고칠 수 있습니다 (5번 rule_config.js).
- **AI가 잘하는 일만 맡긴다.** 정해진 장소를 하랑이 말투로, 그 사람 상황에 맞게 설명하는 것은 AI가 코드보다 잘합니다.
- **AI가 멈춰도 앱은 돈다.** 5단계가 실패하면 승인 대사로 내려가므로 시연이 끊기지 않습니다 (8번).
- 그래서 발표에서는 "AI가 코스를 마음대로 만든다"는 걱정에 **"안전 규칙은 AI가 바꿀 수 없다"**로 답할 수 있습니다.

### 3-3. 피드백과 어떻게 이어지나

- 외부 피드백의 3단계 체인(기상·장소 분석 → 퀘스트 기획 → 하랑이 페르소나)과 대응시키면 이렇습니다 (11번).

| 피드백의 단계 | 우리 흐름 | 차이 |
|---|---|---|
| 기상·장소 분석 에이전트 | 2~4단계 (코드) | 우리는 에이전트가 아니라 **규칙**으로 둠. 안전 판단이라서 |
| 퀘스트 기획 에이전트 | 미션 내용 (장소별로 미리 정함) | 생성하지 않고 팀이 DB에 넣음 (명세 1-3 결정 "미션 종류는 장소별") |
| 하랑이 페르소나 에이전트 | 5단계 (AI) | 같음. 단 P0는 승인 대사 |
| (없음) | 6단계 검수 (코드) | 우리가 더한 것. 생성 결과를 그대로 보이지 않음 |

- 발표 피드백의 "AI Agent로 하려는 것"에는 "장소 선택이 아니라 **설명과 대화**(5단계, F-14 질의 P1)"라고 답합니다.

### 3-4. 발표 때 정직하게 말할 것

- "6단계 흐름은 **설계**이고, 지금 동작하는 것은 2·3단계(날씨 판정, 장소 거르기)와 고정 경로 선택입니다."
- "문장 생성은 지금 승인 대사로 시연하고, AI 생성은 다음 단계(P1)입니다."
- 이렇게 나누지 않으면 "AI가 어디 있냐"는 질문에 시연으로 답하지 못합니다.

## 4. 흐름도에 그대로 쓸 문구 (후보)

```
[입력] 날씨 · 시간대 · 연령대 · 테마
   ↓
[규칙 판정 · 코드] 폭염이면 실내 모드
   ↓
[장소 필터 · 코드] 검수된 장소 DB에서 모드·연령대에 맞는 곳만
   ↓
[장소 선택 · 코드] 정해진 기준으로 3곳
   ↓
[문장 생성 · AI] 3곳의 제목 · 설명 · 이유
   ↓
[검수 · 코드] 허용 키워드 · 길이 확인 → 실패하면 승인 대사
```

- 아래 한 줄: "AI는 장소를 고르지 않고, 고른 장소를 설명합니다. 안전 규칙은 AI가 바꿀 수 없습니다."

## 결정 필요

1. 첫 발표의 핵심 고객: 20~30대(혼자·친구, 이 문서 추천) / 40~50대 가족.
2. 장소 표에 열을 추가할지: 테마 태그, 세그먼트 적합도, 화장실, 계단·경사.
3. 추천 API에 연령대·테마 입력을 추가할지, 추가하면 언제(P0/P1).
4. 4단계를 지금처럼 "고정 경로"로 둘지, 설명 페이지의 점수 선택으로 바꿀지.
5. 6단계 검수 규칙: 허용 키워드 목록, 문장 길이, 실패 시 기본 문장.
6. 세그먼트별 데모 코스 3개를 누가 언제 만들지.
