2026-11-27 발표 · 초안 v1

하랑이 이야기와, 그 뒤에서 일하는 에이전트

스토리보드 중심 + 에이전트 구조와 현재 상태

설계와 시연용 화면을 구분해서 보여 드립니다.

오늘은 두 가지를 말씀드립니다. 앱에서 이용자가 겪는 이야기(스토리보드)와, 그 이야기 뒤에서 일하는 에이전트입니다.

먼저 정직하게 짚고 시작합니다. 에이전트는 6개로 설계를 마쳤고, 실제로 도는 것은 그중 일부입니다. 설계와 구현을 나눠서 보여 드리겠다고 미리 말해 두면 뒤의 시연이 신뢰를 얻습니다.

오늘 말씀드릴 순서

  • 1. 이용자가 겪는 이야기 (스토리보드)
  • 2. 화면마다 뒤에서 일하는 에이전트
  • 3. 설계 원칙: LLM이 쓰고, 코드가 거부한다
  • 4. 실패해도 안전한 구조와 실행 기록
  • 5. 시연 (시연용 가짜 모델)
  • 6. 지금 어디까지 됐고, 무엇이 남았나

시간은 약 5~7분 기준입니다 [확인 필요: 실제 배정 시간]. 1~2번이 스토리보드, 3~6번이 에이전트입니다.

청중이 스토리보드를 이미 본 적이 있다면(11/18 발표) 1번은 한 장으로 줄이고 2번부터 시간을 씁니다.

1. 이용자가 겪는 이야기

① 타이틀→② 가입→③ 로그인→홈: 오늘의 길 고르기→여행: 길 안내·도착→미션: 도장→컷씬·앨범→일기
  • 하랑이가 장부(앱)를 열어 주는 이야기로 시작합니다.
  • 이용자는 낯선 탐험가에서 길동무가 됩니다.
  • 장소에 도착하면 능금 도장을 찍고, 완주하면 컷씬과 기록이 남습니다.
  • 안전 정보(특보, 쉼터 운영 시간)는 이야기 설정보다 먼저입니다.

스토리보드는 앱의 클릭 하나하나에 이야기를 입히는 문서입니다. 근거: storyboard/game_flow_story_v1.md (타이틀부터 홈까지), storyboard/app_screen_storyboard_v1.md.

이용자가 직접 메모를 쓰는 일은 없고 기록은 자동입니다. 그래서 "기록 정리" 에이전트가 필요해집니다 (다음 장에서 연결).

용어 주의: "능금 도장"은 방문 인증으로 찍히는 것이고, 하랑이가 들고 다니는 "능금"은 실제 과일입니다 (사용자 결정 2026-11-16).

화면 이미지를 넣고 싶으면 11/18 자료 presentation/20261118/assets/storyboard_project/ 또는 storyboard/ 폴더의 목업 html을 쓸 수 있습니다. 이 초안에는 넣지 않았습니다.

2. 화면마다, 뒤에서 일하는 에이전트

이용자 화면뒤에서 일하는 에이전트하는 일
홈: 오늘의 길 고르기코스 설계날씨·영업·이동 시간을 보고 길 3곳을 짭니다
도착 → 미션미션 (퀴즈·인증샷·영수증)장소 설명, 과제 출제, 판정. 도장은 코드가 기록
하랑이와 대화하랑이와 이야기하기질문·규칙·잡담에 근거를 보고 답합니다
완주 후 일기기록 정리방문 기록으로 일기를 씁니다
완주 후 카드하랑이 카드미션 결과마다 카드 이미지를 만듭니다
(운영자) 장소 관리장소 DB 갱신새 장소 후보를 찾고, 사람이 승인해야 반영

설계 기준: plan/spec/agent_architecture_v2.md (팀 확인 전 초안)

이 장이 두 주제를 잇습니다. 스토리보드의 장면이 에이전트 하나하나와 대응된다는 점을 보여 줍니다.

에이전트는 6개입니다. 사용자 결정(2026-11-24)이며 팀 확인 전입니다. 이전 안(v1)은 3개였습니다.

"장소 DB 갱신"은 이용자 화면에 보이지 않는 운영자용 에이전트입니다. LLM이 후보를 찾아도 사람이 승인하기 전에는 DB에 쓰지 않습니다.

조심: 이 표는 설계입니다. 지금 실제로 도는 것은 코스 설계(기존 길 구성)와 하랑이 대사(시작·도착·브리핑 장면)뿐입니다. 6번 장에서 다시 말합니다.

3. 설계 원칙: LLM이 쓰고, 코드가 거부한다

LLM이 하는 일

  • 장소 설명, 코스 이유, 과제 출제
  • 대화 답변, 일기, 카드 그림

코드가 하는 일 (거부권)

  • 영업 여부, 이동 시간, 안전
  • GPS 반경, 중복 제출, 도장·점수
  • 금칙어, 근거 id 확인
  • 에이전트마다 순서가 정해진 그래프를 따릅니다. 최상위 감독자 LLM은 두지 않습니다.
  • 어느 단계가 실패해도 마지막에는 미리 만든 안전한 결과로 내려갑니다.

근거: agent_architecture_v2.md 1장 ("LLM이 찾고 쓰고, 코드가 거부권을 가집니다").

왜 이렇게 하나: LLM은 그럴듯하게 틀릴 수 있습니다. 닫힌 가게를 추천하거나 이용자가 안 갔는데 도장이 찍히면 안 됩니다. 그래서 사실과 안전과 점수는 코드가 최종 판정합니다.

[결정 필요] 미션 판정을 LLM(Gemini)이 의견으로 내고 코드가 확인한 뒤 기록하는 안은 dev/CLAUDE.md의 기존 규칙("LLM은 판정에 관여하지 않음")과 충돌합니다. 팀 결정 전이므로 "도장과 점수는 코드가 확인한 뒤 기록한다"까지만 말합니다.

에이전트 전체 구조 (설계)

위에서 아래로 읽습니다. 공통 관문(로그인, 요청 한도, 일일 한도, 호출 예산) → 에이전트 6개 → 장소 DB(읽기), 실행 기록 DB(추가만) → 관리자 웹.

한 줄 강조: "모든 단계의 LLM 결과와 코드 판정이 실행 기록에 남습니다." 다음 장에서 이어집니다.

구조도 원본: plan/spec/agent_architecture_v2_images/agent_overall_v2.svg. 에이전트별 상세 구조도(agent_course_v2.svg, agent_mission_v2.svg 등)도 같은 폴더에 있습니다.

코스 설계 에이전트

하는 일 테마·날씨·영업·이동 시간을 보고 길 3곳을 짭니다.

LLM 연구자(테마별 근거 수집), 기획자, 작성자(이유 문장), 평가자

코드(거부권) 테마 관문, 근거 합치기, 확인자(영업·T맵 이동 시간), 문장 검증

실패하면 시도 횟수를 다 쓰면 대체 코스, 막히면 기존 composeRoute

현재 일부 기존 길 구성 그래프만 동작. 이 구조는 설계

흐름: 테마 관문(코드)이 연구자(LLM)를 고르고, 근거를 합친 뒤 기획자 ⇄ 확인자가 길을 다듬습니다. 확인자가 닫힌 곳을 거부하면 기획자가 장소를 바꿉니다(되돌이). 작성자 → 검증 → 평가자를 통과하면 끝입니다. 근거: agent_architecture_v2.md 4-1장, course_agent_design_v1.md.

좌표는 LLM·외부 검색에 보내지 않습니다 (dev/CLAUDE.md 절대 규칙 1). T맵은 서버가 직접 부릅니다. 지금은 DB에 있는 장소만 코스에 넣습니다.

[중요] 현재 실제 동작은 기존 길 구성 그래프(compose_graph: 구성 → 검증 → 재시도 → 규칙 폴백)입니다. v2 구조는 course_agent_design_v1.md 10장의 7단계 PR로 구현할 계획이며 코드는 아직 없습니다.

미션 에이전트 (전체 흐름)

하는 일 장소 한 곳마다 한 번 돕니다. 장소를 설명하고, 미션 종류를 골라 종류별 에이전트로 보냅니다.

LLM 장소 설명, 설명 검토, 종류 고르기

코드(거부권) 도착 확인(GPS 반경), 설명 검증(근거 id·금칙어·길이), 허용 종류 거르기, 도장 기록

실패하면 고정 설명과 준비된 과제로 내려감. 판정 실패 시 도장 보류

현재 설계만 구조도와 시연용 시나리오

흐름: 도착 확인(코드) → 장소 설명(LLM) → 설명 코드 검증 → 설명 LLM 검토 → 종류 고르기(LLM) → 종류별 에이전트 → 도장 기록(코드). 근거: agent_architecture_v2.md 4-2장.

종류 고르기는 장소와 이용자 상황을 보고 퀴즈·인증샷·영수증 중 하나를 고르고, 코드가 그 장소에서 허용되는 종류만 남깁니다 (예: 영수증은 구매할 수 있는 곳만). 허용 종류를 어디에 저장할지는 [확인 필요].

[결정 필요] 장소 사이(다음 장소로 가는 길) 설명을 이 에이전트가 맡을지. 현재 페르소나의 "장소의 사연이나 유래는 넣지 않는다" 규칙(harangi_persona.js:19)이 장소 설명과 맞지 않아 설명용 규칙을 따로 둘지도 정해야 합니다.

새 장소의 미션은 검수 전에는 도장과 연결하지 않습니다 [결정 필요].

미션 · 퀴즈 에이전트

하는 일 장소 사실로 문제와 정답을 내고, 이용자의 답을 채점합니다. 제출 전에 힌트를 줄 수 있습니다.

LLM 출제, 출제 검토, 채점(Gemini), 힌트 작성·검토

코드(거부권) 출제 검증, 제출 점검(형식·시도 횟수), 판정 확인, 힌트의 정답 노출 거부

실패하면 준비된 과제로 내려가거나 도장 보류

현재 설계만

출제 → 출제 코드 검증 → 출제 LLM 검토 → 이용자 제출 → 제출 점검 → 판정(Gemini) → 판정 확인(코드) → 도장 기록.

힌트는 퀴즈에만 있습니다. 정답 문자열은 힌트 작성의 입력에서 제외하고, 힌트 코드 검증이 정답 노출을 거부하고, 힌트 LLM 검토가 도움이 되는지 봅니다.

Gemini가 통과라고 해도 판정 확인(코드)이 GPS 반경, 중복 제출, 한 장소 한 번만 도장을 다시 확인합니다. 시간이 지나거나 판정하지 못하면 도장을 보류하고 저절로 통과시키지 않습니다.

[결정 필요] 미션 판정을 LLM이 하도록 dev/CLAUDE.md 34행을 바꿀지. 이 문서는 변경을 전제로 쓰였고 dev/CLAUDE.md는 아직 고치지 않았습니다.

미션 · 인증샷 에이전트

하는 일 찍을 대상과 구도를 안내하고, 제출한 사진이 과제에 맞는지 봅니다.

LLM 출제, 출제 검토, 이미지 판정(Gemini 이미지 입력)

코드(거부권) 제출 점검(GPS 반경·중복·EXIF 제거), 판정 확인, 도장 기록

실패하면 횟수를 다 쓰면 도장 보류(폴백). 도움말은 안내문 다시 보기(코드)

현재 설계만 사진 입력 모델·한도 확인 필요

사진은 서버에서만 Gemini로 보냅니다. 키는 앱에 두지 않습니다. 보내기 전에 코드가 EXIF를 제거합니다. 원본은 저장하지 않고 판정 결과·이유·사유 코드만 실행 기록에 남깁니다.

[결정 필요] 이용자 사진이 외부로 나가므로 "LLM에 보낼 개인 정보 범위"(D-17)에 사진을 넣어 팀 확인을 받아야 합니다. 이미지 호출은 글 호출보다 한도를 더 쓸 수 있습니다 [확인 필요].

[확인 필요] 설치된 @langchain/google-genai에서 이미지 입력을 쓰는 방법과 사진 입력이 되는 모델은 공식 문서로 확인한 뒤 씁니다 (dev/CLAUDE.md 절대 규칙 7).

미션 · 영수증 에이전트

하는 일 어디서·무엇을·언제 샀는지 조건을 내고, 영수증 사진이 조건에 맞는지 봅니다.

LLM 출제, 출제 검토, 이미지 판정(Gemini: 장소·날짜 확인)

코드(거부권) 제출 점검(결제 정보 가림·중복), 판정 확인, 도장 기록

실패하면 횟수를 다 쓰면 도장 보류. 도움말은 조건 다시 보기(코드)

현재 설계만 결제 정보 가리는 방법 미정

영수증에는 결제 정보가 있어 가장 조심합니다. 보내기 전에 코드가 결제 정보를 가리고, 가려지지 않았으면 제출 점검이 PAYMENT_NOT_MASKED로 거부합니다 (관리자 화면 시연 시나리오에 있음). 가리는 방법은 [확인 필요].

영수증은 구매할 수 있는 장소에서만 허용 종류로 남습니다. 원본은 저장하지 않습니다.

[결정 필요] 사진·영수증을 Gemini로 보내는 범위(D-17).

하랑이와 이야기하기 에이전트

하는 일 질문 답변, 게임 규칙 답변, 잡담을 맡습니다. 근거가 없으면 "잘 모르겠어요"라고 합니다.

LLM 분류, 답변 작성

코드(거부권) 안전 점검(위험 표현은 고정 안내), 근거 조회(읽기 도구만), 답변 검증

실패하면 검증이 계속 실패하면 고정 문장(승인 대사)

현재 일부 기존 하랑이 대사는 시작·도착·브리핑 장면만. 자유 대화는 설계

흐름: 안전 점검(코드) → 분류(LLM) → 근거 조회(코드) → 답변 작성(LLM) → 답변 검증(코드) → 보내기. 정답 문자열은 입력에서 제외합니다.

장소 설명과 힌트는 미션 에이전트가 맡고, 이 에이전트는 질문·규칙·잡담만 맡습니다. 근거: agent_architecture_v2.md 4-3장.

기존 하랑이 대사 그래프(harangi_graph: 에이전트 ↔ 조회 도구 → 검증 → 폴백)가 일부 동작하고 있습니다. 하랑이 말투는 brand/character/profile/harangi_character.md와 금칙어를 따릅니다.

기록 정리 에이전트

하는 일 완주 직후 한 번, 방문 기록으로 일기를 씁니다.

LLM 일기 작성

코드(거부권) 사실 묶음 만들기, 검증(사실 묶음 밖 문장 금지), 일기 저장

실패하면 틀 일기

현재 설계만 방문·도장 저장이 먼저 필요

흐름: 사실 묶음(코드) → 일기 작성(LLM) → 검증(코드) → 일기 저장. 이용자가 직접 메모를 쓰는 일은 없고 기록은 자동입니다 (스토리보드 전제).

방문·도장·퀴즈 결과가 서버에 저장된 뒤에 동작합니다. 이 저장이 현재 dev에 있는지는 확인하지 못했습니다 [확인 필요]. 옛 문서(v1 3장) 기준으로는 없었습니다.

하랑이 카드 에이전트

하는 일 코스를 완주하면 미션 결과마다 하랑이 카드 이미지를 한 장씩 만듭니다.

LLM 프롬프트 작성, 이미지 생성(Gemini), 이미지 검토(Gemini 비전)

코드(거부권) 사실 묶음(민감 소재 거르기), 이미지 검증(크기·형식), 카드 조립(템플릿), 카드 저장

실패하면 미리 만든 고정 카드 틀. 이미지 생성이 실패해도 카드는 나옴

현재 설계만 이미지 생성 가능 여부·한도 확인 필요

코스 테마(코스 설계가 정한 값)와 미션 결과를 받아 미션마다 프롬프트를 씁니다. 캐릭터는 고정 시트(brand/character/)를 따르고 프롬프트는 brand/character/prompts.md에 기록합니다 (CLAUDE.md).

이용자 사진은 카드 재료로 쓰지 않습니다. 폭염·한파 안전 정보나 민감한 역사 소재는 카드 소재로 쓰지 않습니다 (CLAUDE.md 민감한 소재).

이미지 생성은 호출이 가장 비쌉니다. 완주 한 번에 미션 수만큼 늘어나서 호출 수 상한과 진행 표시가 필요합니다 [결정 D-19]. Gemini 이미지 생성이 설치된 라이브러리·무료 한도에서 되는지, 기준 이미지로 캐릭터를 맞출 수 있는지는 [확인 필요].

[결정 필요] 생성 이미지를 공개 전에 관리자가 검수할지, 하랑이 한마디를 LLM이 쓰게 할지.

장소 DB 갱신 에이전트

하는 일 운영자가 돌리는 배치입니다. 새 장소 후보를 찾고, 사람이 승인해야 DB에 반영됩니다.

LLM 후보 발굴(웹 검색), 기획자

코드(거부권) 확인자(출처·영업·좌표), 후보 보관, DB 반영(승인된 것만)

실패하면 확인에 계속 실패한 후보는 폐기(기록만 남김). 사람이 거절하면 보류

현재 설계만 관리자 화면에 승인 화면 필요

LLM은 장소 DB(places)에 직접 쓰지 않습니다. 후보 보관 표에 쓰고, 승인된 것만 코드가 places에 반영합니다.

식민지·전쟁 소재 장소는 주의로 표시하고 사람이 검수합니다. 실존 인물과 실제 가게 이름은 허가 범위를 확인한 뒤 씁니다 (CLAUDE.md).

웹 검색 도구는 아직 없고, 무료 한도와 믿을 출처 목록을 먼저 확인해야 합니다 [확인 필요]. 운영자 웹의 형태는 D-03 미결정입니다.

4. 모든 단계가 기록으로 남습니다

실행 기록 (추가만)

  • 어느 단계에서 무엇을 썼나
  • 걸린 시간, 호출 수, 토큰
  • 코드가 왜 거부했나 (사유 코드, 예: NOT_OPEN)
  • 고치거나 지우지 않음
  • 좌표·계정·사진 원본은 기록하지 않음

관리자 화면 (/admin)

  • 실행 목록·단계별 타임라인
  • 구조도에서 지금 도는 노드가 깜빡임
  • 접속 현황
  • 관리자 전용 아이디·비밀번호 로그인

구현·병합됨 공통 기반과 관리자 화면 (PR #281), 서버 테스트 599개 통과

근거: agent_architecture_v2.md 5장, 병합된 PR #281(dev/server/src/agents/common/, dev/server/src/admin/).

왜 필요한가: 에이전트가 왜 그렇게 답했는지, 어느 단계에서 막혔는지 사람이 볼 수 있어야 고칠 수 있고 신뢰할 수 있습니다.

개인정보: 좌표, 계정 식별자, 사진·영수증 원본, 결제 정보는 기록하지 않습니다 (CLAUDE.md 개인정보). 이용자 연결은 익명 키(해시)로 합니다.

관리자 접근은 서버 변수(ADMIN_*)가 설정돼야 열리고, 앱 이용자 토큰으로는 들어갈 수 없습니다. 기록 표 SQL의 실제 DB 적용은 아직 확인하지 못했습니다 [확인 필요].

5. 시연: 코드가 거부하는 장면

  • 시나리오 A: 영업 확인 실패 → 장소 교체 → 통과
  • 시나리오 B: 확인이 계속 실패 → 시도 소진 → 대체 코스
  • 화면에서 볼 것: 구조도의 깜빡임, 단계별 시간, 거부 사유 코드

※ 시연용 가짜 모델입니다. 실제 Gemini 결과가 아닙니다.

로컬 서버 http://127.0.0.1:3000/admin/ (ADMIN_DEV_OPEN=true) · 포트는 [확인 필요]

시연 직전에 "가짜 LLM으로 구조도를 따라 도는 시연용"이라고 먼저 말합니다. 근거: dev/server/src/admin/scenarios.js 머리말. 토큰 수도 가짜 값입니다.

순서: (1) "코스 설계 · 영업 확인 실패 후 장소 교체" 실행 → 확인자 노드가 NOT_OPEN으로 거부 → 기획자로 되돌아감. (2) "시도 횟수 소진 후 대체 코스" 실행 → 대체 코스로 끝.

준비: 로컬 서버를 미리 켜 두고 리허설 1회. 시연용이라 Gemini 호출·비용이 없습니다. 실패에 대비해 화면 캡처를 이 장 뒤에 붙여 두는 것을 권합니다 (아직 안 만듦).

배포 서버에서 보여 주려면 SQL 적용과 Railway 변수 설정이 먼저 필요합니다. 발표 전에는 로컬 시연을 권합니다 [결정 필요].
