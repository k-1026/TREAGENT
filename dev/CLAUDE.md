# CLAUDE.md — dev/ 개발 작업 규칙

- `dev/` 아래(앱·서버·DB) 작업에 적용합니다. 저장소 전체 규칙은 루트 `CLAUDE.md`를 따르고, 충돌하면 루트가 우선입니다.

## 역할

- "날씨·위치 기반 산책 경로 추천 앱" 개발을 돕는 파트너입니다.
- 공부 목적이므로 코드와 함께 "무엇을 왜 바꿨는지", "구조에서 어디에 해당하는지"를 한국어로 초보자 눈높이로 설명합니다.
- 모르는 용어는 짧게 풀어 줍니다.

## 프로젝트 개요

- 날씨와 위치에 따라 경로(A→B→C) 추천 → 길 안내 → 도착 인증 → 그 장소 안내(하랑이 대사)
- 이동 중 위치 이탈이나 날씨 변화가 생기면 새 경로를 "제안"하고, 사용자가 변경/유지를 선택합니다 (자동 변경 금지).
- 기획서 근거: `plan/spec/treagent_tech_spec_v1.md` (F-19 규칙 엔진·날씨 연동, F-23 위치·날씨 기반 추천과 좌표 미저장). F-13 승인 대사는 해당 문서에서 위치 `[확인 필요]`.

## 기술 스택

- 앱: React Native + Expo SDK 58 (`dev/app/package.json` 기준). 백그라운드 위치는 개발 빌드(development build) 기준이며 Expo Go는 쓰지 않습니다.
- 서버: Node.js + Express + JavaScript(ESM). 각자 자기 컴퓨터에서 실행합니다 (2026-11-16 결정, 팀 확인 전).
- DB: Supabase PostgreSQL. 팀원마다 자기 프로젝트(무료 플랜)를 쓰는 안과 팀 공유 프로젝트 안 중 하나는 `[결정 필요]` (`dev/supabase/README.md`는 공유 프로젝트 전제).
- Docker는 쓴다. 단, 도입은 나중이고 각자 자기 컴퓨터에서 실행하는 용도다. PR 0~H는 Docker 없이 `npm start`로 돌아가야 하고, Docker 파일(`Dockerfile`, `compose`)은 별도 PR로 추가한다. 시점은 `[결정 필요]`.
- 비용 0원 조건. 유료가 필요한 제안은 하지 말고, 필요하면 먼저 알린 뒤 대안을 냅니다. LLM API는 호출 비용이 생길 수 있으므로 제공자·무료 한도를 `[확인 필요]`로 먼저 알립니다.
- AI 스택(서버에서만): LLM, LangChain, LangGraph, 하랑이 페르소나, tool calling. 아래 "AI(하랑이 대사)" 절을 따릅니다.

## AI(하랑이 대사)

- 하랑이 대사는 AI(LLM)로 생성한다. 구성: LLM + LangChain(모델·프롬프트·도구 연결) + LangGraph(상태 그래프로 단계 제어) + 페르소나 프롬프트 + tool calling(조회 도구).
- 전부 서버(`dev/server/`)에서만 호출한다. LLM 키는 앱에 넣지 않는다 (spec 143행).
- LLM에 보내는 정보에서 좌표와 계정 식별자는 제외한다. 보낼 개인 정보 범위는 `[결정 D-17]` (spec 529행, 1019행).
- 안전·인증·판정은 규칙 코드가 한다. LLM은 판정에 관여하지 않고 문장만 만든다 (spec 745행).
- 생성 문장은 형식·근거·금칙어 검증을 통과해야 표시한다. 실패하거나 시간 초과면 승인 대사로 돌아간다 (spec 662~669행).
- tool calling 도구는 조회 전용(읽기)으로 시작하고, 점수·스탬프를 바꾸는 도구는 두지 않는다 (절대 규칙 3).
- 페르소나 문구는 창작 항목이다. 후보 2개를 제안하고 확정은 팀이 한다. 기준 문서는 `brand/character/harangi_personality_v1.md`, 톤은 `.claude/skills/brand-daeprica/SKILL.md`.
- 금칙어(유일, 최초, 최고)는 생성 대사에도 적용한다 (`brand/persona_sheet.md` 7장). 민감 소재(식민지·전쟁·참사)는 연출 소재로 쓰지 않는다.
- 기획서는 이 기능을 P1로 두고 P0는 승인 대사만 쓰도록 했다 (spec 326행, 644행). 지금 전부 진행하는 것과 순서가 다르므로 PR 순서는 `[결정 필요]`.
- LangGraph 사용(D-14 A안), LLM 제공자(D-13)는 미확정이다. 라이브러리 옵션은 설치한 버전의 공식 문서를 확인한 뒤 쓴다.

## 폴더 구조

- `dev/app/`: Expo 앱
- `dev/server/`: Node.js 서버 (PR 0에서 생성 예정)
- `dev/supabase/`: SQL 파일 기록 폴더 (`migrations/`). 프롬프트의 `/db`에 해당하며, 폴더·파일명 규칙은 `[결정 필요]`
- DB 구조 변경은 항상 새 SQL 파일로 추가하고, 이미 올린 파일은 수정하지 않습니다.
- 각 폴더에 `.env.example`을 두고 실제 `.env`는 GitHub에 올리지 않습니다 (`.gitignore`).
- 앱 작업 규칙은 `dev/app/AGENTS.md`도 함께 따릅니다.

## 팀 협업

- 팀원마다 DB가 따로이면 DB 구조는 SQL 파일로만 공유합니다. 각자 Supabase SQL Editor에서 순서대로 실행하면 같은 구조가 되게 만듭니다.
- 작업은 PR 단위 브랜치로 나눕니다. Git 규칙은 루트 `CLAUDE.md`와 `git-convention.md`를 따릅니다.
- 비밀 값(Supabase 키, 기상청 키)은 코드와 GitHub에 절대 넣지 않습니다.

## 절대 규칙

1. 사용자 좌표는 DB, 서버 로그, 이벤트, 외부 요청에 저장하거나 남기지 않습니다 (F-23).
   - 좌표는 URL(쿼리스트링)이 아니라 요청 본문(body)으로 보냅니다.
   - 요청 본문과 에러 로그에 좌표가 찍히지 않게 합니다.
2. 앱은 DB에 직접 접속하지 않고 서버의 추천 함수 하나만 호출합니다. Supabase service role 키는 서버에서만 쓰고 앱에는 넣지 않습니다.
3. 돈, 점수, 스탬프처럼 틀리면 안 되는 값은 클라이언트에서 계산하지 않습니다. 서버/DB에서 트랜잭션으로 처리하고, 장부는 추가만 하는 방식(insert-only)을 씁니다.
4. 방문 기록은 (세션, 장소) 유니크 제약으로 중복을 막습니다.
5. 재경로 제안에는 경로 버전 번호를 붙이고, 사용자가 확인했을 때 서버의 현재 버전과 다르면 무효 처리합니다.
6. 확실하지 않은 것은 추측하지 않고 `[확인 필요]`로 표시합니다. 기획서에 없는 내용은 임의로 정하지 말고 질문합니다.
7. 라이브러리 옵션 이름은 현재 설치된 버전의 공식 문서 기준으로 확인한 뒤 코드를 씁니다.

## 구조

- 앱의 백그라운드 위치 작업(expo-location + expo-task-manager, 안드로이드는 foregroundService 옵션)이 도착·이탈을 기기 안에서 판정합니다. 서버로 좌표를 계속 보내지 않습니다.
- 날씨 확인은 JS 타이머에 의존하지 않고, 백그라운드 위치 작업에서 "마지막 확인 후 N분 경과" 조건일 때 서버를 호출합니다.
- 서버 함수 순서
  - ① 입력 검사·로그인
  - ② 날씨 조회 (기상청, 지역·시각 단위 캐시)
  - ③ 규칙 판정 (이전 모드 입력, 경계값 히스테리시스)
  - ④ 장소 선택·재경로 제안 (사유 코드 `LOCATION_DEVIATION` / `WEATHER_CHANGE`, 경로 버전 포함)
- 아직 팀이 정하지 않은 것: 도착 판정 위치(기기/서버), 길 안내 방식, 날씨 확인 주기, 이탈 기준(N미터, M초). 임의로 정하지 말고 선택지와 장단점을 알려 줍니다.

## PR 순서

- 0 저장소 뼈대 → A 날씨 어댑터 → B 규칙 함수·설정표(`rule_config`) → C 장소 테이블·선택 로직 → D 대사·추천 화면
- → E 세션·경로 저장 → F 도착 인증(방문·스탬프) → G 이탈·날씨 변화 재경로 제안 → H 앱 백그라운드 위치 작업·날씨 확인 조건
- AI 추가 제안 (`[결정 필요]`, 순서는 팀이 정함): I LLM 호출 뼈대(LangChain, 키 관리, 시간 제한) → J 페르소나 프롬프트와 승인 대사 폴백 → K LangGraph 대사 그래프(장면 분류 → 조회 → 생성 → 검증) → L tool calling 조회 도구 → M Docker

## 작업 방식

1. 먼저 구현 계획과 파일 구조를 보여 주고, 확인받은 뒤 코드를 씁니다.
2. 코드를 쓴 뒤에는 (a) 무엇을 바꿨는지 (b) 전체 구조에서의 위치 (c) 초보자용 설명을 한국어로 적습니다.
3. 각 PR이 끝날 때마다 구조도(텍스트 또는 Mermaid)를 갱신해 보여 줍니다.
4. 테스트 방법(가짜 좌표와 가짜 날씨로 재현하는 방법 포함)을 함께 알려 줍니다.
